## 0. 结论摘要

**一句话画像**：一个以 Next.js 静态导出承载的品牌型 3D 影像画廊，视觉与设计系统完成度高，但存在「首屏无 SSR 内容、移动端不可浏览、渲染循环内触发 React 重渲染、质量门禁度量范围失真」四类结构性问题。

**总体判定**：技术可行、可继续演进，不建议在当前质量门禁结论上直接宣布「稳态达标」。核心风险不在架构选型，而在**核心交互完整性**与**质量证据可信度**。

| 维度 | 结论 | 关键证据 |
| ---- | ---- | ---- |
| 可构建性 | 通过 | `pnpm build` 静态导出成功，50 项预缓存 |
| 类型/规范 | 通过 | `tsc --noEmit` 0 错误；ESLint 0 输出 |
| 单元测试 | 通过（范围有限） | 13 套件 / 140 用例全绿；覆盖范围仅为 `lib/` |
| E2E | 未能本地复现 | 缺 Playwright 浏览器二进制，且下载被锁/网络阻塞 |
| 依赖安全 | 通过 | `pnpm security:check` 0 漏洞 |
| 运行性能 | 高风险（代码级） | `useFrame` 内每帧 `setState`；全量纹理加载；DPR 未限 |
| SEO/首屏 | 高风险 | 导出 HTML 主体为空，页面组件在 hydration 前返回 `null` |
| 移动端核心功能 | 高风险 | 画廊仅监听 `wheel` 与 `keydown`，无触摸滚动 |

## 2. 深度维度分析

### 2.1 架构合理性

**现状**
- 采用「静态导出 + 客户端状态层 + 浏览器持久化」架构，无服务端依赖，部署面最小。
- 领域 store 拆分清晰，`useSyncExternalStore` 与 React 19 并发渲染兼容，避免 Context 深层传递。
- 组件按 `media-space`、`widgets`、`ui` 分层，边界基本可读。

**问题**
1. 页面级架构把「全部功能」静态挂载到同一棵树：`InfiniteGallery`、`ConfigPanel`、`MediaSpace`、`WidgetLayer`、4 个全局浮层全部首屏加载（[page.tsx](../../app/page.tsx#L126-L358)）。其中媒体空间默认 `isOpen: true`（[store.ts](../../lib/media-space/store.ts#L110-L117)），会直接挂载 ArtPlayer 与音频元素。
2. 配置系统与主题系统同时写 `<html>` 内联 CSS 变量：`applyConfigToDOM`（[config-store.ts](../../lib/config-store.ts#L161-L188)）与 `applyThemeToDOM`（[version-store.ts](../../lib/version-store.ts#L303-L311)）都会写 `--warm-primary`、`--ambient-*`。最终值取决于 effect 执行顺序，切主题会覆盖用户自定义色，重放配置又会覆盖主题色。
3. 宿主桥接既是「能力协商」又是「网络代理」又是「持久化同步」，职责偏多（[host-bridge.ts](../../lib/host-bridge.ts#L102-L251)），但边界封装尚可，暂不构成阻断。

**影响**
- 首屏资源竞争严重，移动端低端机首屏与帧率风险高。
- 主题/配置存在「谁最后写谁生效」的隐性冲突，属于可复现的设计缺陷风险。
- 后续若要接入真实 AI 标注/后端同步，需要先把桥接层拆分为 capability / proxy / storage 三个接口。

### 2.2 代码质量

**现状**
- 全量通过 `tsc` 严格检查与 ESLint，未发现显式 `any`、未发现硬编码密钥。
- 状态恢复普遍做了运行时校验（版本、媒体会话、组件、推荐、标注等），异常路径有 try/catch，质量高于一般展示型项目。
- 多数文件有统一文件头注释。

**问题**
1. **死代码规模大**：55 个 `components/ui` 文件中 46 个未被任何业务代码引用，合计 5,762 行；`FloatingMediaPlayer.tsx` 1,026 行无引用；`styles/globals.css` 125 行无引用；`theme-provider.tsx` 无引用。合计约 6,900+ 行，占 TS/TSX 总量约 39%。
2. **死依赖**：`recharts`、`embla-carousel-react`、`vaul`、`input-otp`、`react-day-picker`、`react-hook-form`、`react-resizable-panels`、`cmdk`、`sonner`、`next-themes`、`@react-three/postprocessing` 仅被未引用文件使用或完全未使用，增加安装体积与供应链面。
3. **重复实现**：`hooks/use-toast.ts` 与 `components/ui/use-toast.ts` 重复；`styles/globals.css` 与 `app/globals.css` 重复。
4. **Hook 依赖缺陷**：`MediaSpace` 的本地媒体恢复 effect 依赖 `[currentAudio?.cover, currentVideo?.cover]`，依赖变化会先执行清理并 `revokeObjectURL` 全部本地 URL，随后又因 `hydratedRef` 提前返回、不再重建（[MediaSpace.tsx](../../components/media-space/MediaSpace.tsx#L90-L122)）。切换曲目后本地媒体可能失效。
5. **注释与实现不一致**：推荐排序注释称「未浏览作品按原序穿插保留探索性」，实际按分数降序把未浏览作品排到最后（[recommendation-store.ts](../../lib/recommendation-store.ts#L168-L186)）。

**影响**
- 阅读与二次开发成本被死代码显著放大；依赖审计与升级需要为无用包付出成本。
- 本地媒体恢复属于真实功能缺陷，不是风格问题。

### 2.4 性能风险

| 风险 | 机制 | 影响 | 判定 |
| ---- | ---- | ---- | ---- |
| React 每帧提交 | `useFrame` 内两次 `setScrollVelocity`，并依赖 state 驱动 plane 位置 | 每帧协调 12 个 plane + 材质更新，移动端易掉帧 | 高 |
| 纹理全量加载 | `useTexture` 一次加载 18 张图（约 6.7MB） | 首屏网络/解码/显存峰值高 | 高 |
| Shader 成本 | 每个片元 5x5（25 次）模糊采样；未限制 `dpr` | 高 DPR 移动端 GPU 压力大 | 高 |
| 媒体空间默认打开 | 首屏挂载 ArtPlayer + audio + 4 个 session 窗口 | 首屏 JS/解码/内存额外开销 | 中高 |
| 全局 store 高频更新 | 拖拽/进度条/timeupdate 都触发整棵媒体空间重渲染 | 交互期间掉帧 | 中 |
| 大资产入库 | `public` 96MB、`.git` 104MB | 克隆与 CI 传输成本高；Pages 产物 98MB | 中 |
| 微基准不代表渲染 | `pnpm benchmark` 仅测纯函数（本次实测 0.003–0.381μs/次） | 不能证明 60fps | 结论受限 |

本次实测基准（darwin arm64 / 16 vCPU / 128GB / Node 22.22.3）：

| 基准 | 中位数 | P95 |
| ---- | ----: | ----: |
| affinityScore | 0.055μs | 0.102μs |
| recommendOrder（12 图） | 0.381μs | 0.532μs |
| clamp | 0.003μs | 0.024μs |
| queue.find（30 曲目） | 0.104μs | 0.127μs |

结论：纯计算路径无瓶颈；**渲染与内存路径尚无有效基线**，需补 WebGL FPS / 首屏 LCP / 长任务实测。

### 2.6 可维护性

**现状**
- 本地一条命令可完成安装、开发、构建、测试；静态产物可用零依赖脚本本地服务。
- 文档数量多，但 `docs/` 不入库，团队外部成员无法获得设计与规范上下文。
- CI 4 Job 结构清晰，但对构建产物重复构建（build 与 e2e 各构建一次）。

**问题与影响**

### 4.3 优化优先级与落地建议

**第一批（先恢复「可用 + 可信」）**
1. 首屏：移除 `isClient` 整页短路，改为「服务端渲染静态外壳（标题/标语/导航/SEO 文本）+ 客户端渐进增强 3D」；或至少提供 `<noscript>` 与首屏骨架。
2. 移动端：为画廊补齐 Pointer/Touch 滑动（复用 `use-media-gestures` 的思路），并处理 `prefers-reduced-motion`。
3. 渲染循环：把 `scrollVelocity`、`autoPlay`、焦点索引改为 `useRef`，`useFrame` 内直接更新 mesh 位置/材质 uniform，禁止 `setState`。
4. 纹理：按可见窗口懒加载、限制 `dpr={[1, 2]}`、卸载时 `texture.dispose()` / `material.dispose()`、增加 `frameloop="demand"`（无交互时降频）。
5. 配置持久化：背景图改存 IndexedDB（复用 `asset-store`），localStorage 只存 `assetId`；写入失败必须用户可见。
6. 修复 `MediaSpace` effect 依赖与 `revokeObjectURL` 生命周期；播放进度与持久化解耦（仅暂停/切歌/卸载时落盘）。

7. Jest 增加 `collectCoverageFrom` 与阈值；CI 改跑 `test:coverage`；文档改为「lib 覆盖率 / 全项目覆盖率」双口径。
8. 修正 `check-docs`：让 CI 能校验入库文档；若 `docs/` 继续不入库，则明确「文档门禁仅覆盖根目录」，不得宣称覆盖团队标规。
9. 修复 split/unified CSS 冲突：二选一，删除 `html[data-layout=split]` 的 fixed+transform 覆盖，保留 `display:contents` 方案。
10. 统一主题与配置的变量所有权（主题提供默认值，配置只覆盖显式修改项；或配置层优先级明确高于主题）。

17. WebXR 要么补渲染循环，要么把入口降级为「能力展示/敬请期待」，避免误导。

### 4.4 可行性与风险评估结论

- **可行性：高**。项目无服务端耦合，改动集中在客户端渲染与状态生命周期；所有建议均可在现有 Next.js + React + shadcn/Radix + pnpm 架构内完成，无需引入 BaaS、无需更换包管理器、无需改 workspace。
- **交付风险：中**。主要风险不是「做不出来」，而是「质量证据不可信」导致带病发布；建议先恢复度量，再谈优化收益。
- **运行风险：中高**。首屏空白与移动端不可浏览直接影响品牌展示；渲染循环内的 React 更新在低端设备上可能造成明显卡顿。
- **安全风险：低到中**。静态站点无服务端攻击面；主要关注宿主桥接的凭证使用、元数据外传告知与 CSP 纵深。
- **不做的后果**：SEO 与移动端体验持续受损；覆盖率与文档门禁继续提供虚假安全感；死代码使后续每次升级都需要额外验证 40% 的无效表面。
